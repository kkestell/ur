# Large frames

## Plan

`docs/agents/plans/2026-09-25-012-large-frames.md`

## Summary

`FrameCodec`'s decoder no longer limits a payload's size, so it decodes every frame its encoder
writes. A prompt with a 20 MB image reaches the server, and the session's snapshot reaches the GUI
after a restart. The plan's goal is met, and OX-0008 is fixed.

Test guarantees: `frames_round_trip` now also owns "a payload over 16 MiB decodes", with a 20 MiB
`JSON` frame. `decoder_rejects_malformed_frames` no longer owns "a payload over 16 MiB is rejected",
a guarantee this change removes. The unknown tag and short `PTY` frame cases stay. The end-to-end
test `a session holding 20 MB of images loads after reopening the GUI` owns the GUI's side; with the
16 MiB limit restored, its prompt fails with "the connection to the daemon closed".

## Decisions

- The ad-hoc script passes the image into the page in 2 MB pieces and then calls the core's
  `request` command with them. `tauri-plugin-wdio-webdriver` resets the HTTP connection when a
  WebDriver request carries the whole 27 MB of base64. That limit belongs to the test tooling, not
  to ur.

- `make e2e` — passed, 35 tests.

## Manual verification

1. The plan's ad-hoc check, a script in `/tmp` that imports `app/e2e/harness.ts`, run against the
   WebDriver build in `target/e2e`. It started a `TestEnvironment`, opened `ur-app`, added a
   workspace and created a session through the core's `request` command, selected the session, and
   sent a prompt with the text `look` and a 20.3 MB PNG of random pixels as image content. It then
   killed `ur-app` and opened it again with the session still selected.

   ```sh
   cd app && CARGO_TARGET_DIR=../target/e2e cargo build -p ur -p ur-fake-server \
     && CARGO_TARGET_DIR=../target/e2e pnpm exec tauri build --debug --no-bundle --features webdriver
   node /tmp/ur-adhoc/large-frames.ts
   ```

   The thread showed the user message with its image and "you said: look (1 image)" about 3 seconds
   after the prompt was sent. After the restart, the sidebar and the same thread appeared, and 50
   samples of the page text over 5 seconds showed neither "Connecting" nor a missing thread. With
   the decoder's old check restored, the same script failed: the daemon logged "frame payload of
   27047819 bytes is too large" and closed the core's socket connection on every attempt WebDriver
   made to send the prompt.
