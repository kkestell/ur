# Large frames

## Goal

Fix OX-0008 in `docs/agents/issues.csv`: a session whose transcript holds more than about 12.5 MB of
image data puts the GUI in a reconnect loop. The session snapshot is one `JSON` frame, and
`FrameCodec`'s decoder rejects any payload over 16 MiB, so the core's `Client` reader stops, the
socket connection closes, and the Link reconnects and subscribes to the same session again. A prompt
with one image over about 12.5 MB fails the same way in the other direction. When this is done,
`FrameCodec` decodes every frame its encoder writes, and sessions with large images show their
thread and accept prompts.

## Related code

- `crates/ur-client/src/frame.rs` — `MAX_PAYLOAD_LEN` and the decoder's check against it. The
  encoder writes any length. `frames_round_trip` and `decoder_rejects_malformed_frames` test the
  codec.
- `crates/ur-client/src/client.rs` — the reader task, which ends at the first decode error.
- `crates/ur/src/daemon/server.rs` — each socket connection's reader, which closes the socket
  connection at the first decode error.

## Decisions

### The frame length is the only size bound

The decoder drops its payload size check. A frame's length is a `u32`, so a payload is at most 4
GiB, which no transcript reaches. Both ends of the socket are ur's own code on the local machine, so
the decoder trusts the length it reads. The other decode errors, an unknown tag and a `PTY` frame
shorter than a terminal ID, stay.

Image attachment size stays unlimited in the editor. Whether the server accepts a large image is the
server's decision, reported as a rejected prompt.

## Naming

- Frame, session snapshot, core, Link, image attachment, rejected prompt — as defined in
  `docs/agents/glossary.md`.

## Test plan

- `frames_round_trip` gains a case: a `JSON` frame with a 20 MiB payload round-trips.
- `decoder_rejects_malformed_frames` loses its "payload over 16 MiB" case and keeps the unknown tag
  and short `PTY` frame cases.
- End-to-end test in `app/e2e/session.test.ts`,
  `a session holding 20 MB of images loads after reopening the GUI`: `Gui.promptWithImage()` builds
  a 20 MiB image in the webview, so it does not cross WebDriver, and prompts the session with it
  through the core's `request` command. After the reply, the GUI is reopened: the thread loads from
  a session snapshot in one frame over 16 MiB, the GUI stays connected, and a new prompt works. It
  fails before this change, when the daemon connection closes.
- Ad-hoc check against the fake server, whose reply echoes the prompt, through the WebDriver build
  in `target/e2e`: create a session, then call the core's `request` command from the webview with a
  `prompt` holding a 20 MB PNG as image content. The thread shows the user message with its image
  and the reply. Restart the GUI with that session selected: the sidebar and thread appear and the
  GUI does not show "Connecting".

## Implementation plan

1. `crates/ur-client/src/frame.rs`: delete `MAX_PAYLOAD_LEN` and the decoder's check against it.
   Extend the `Frame` doc comment: the payload length is a `u32`, and the decoder accepts any
   length.
2. `crates/ur-client/src/frame.rs` tests: the changes in the test plan.
3. `app/e2e/harness.ts`: `Gui.promptWithImage()`. `app/e2e/session.test.ts`: the test in the Test
   plan.
4. The end-to-end suite and the ad-hoc check.
