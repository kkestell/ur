# Agent GUI

## Goal

Build the Agent GUI section of `docs/agents/todo.md`. Today the GUI is one full-window terminal, and
the core connects to the daemon once. When this is done:

- The window shows a sidebar of workspaces and their sessions on the left and the selected session's
  thread, or the terminal, on the right, as in the thin GUI wireframe. The no-connection,
  no-workspace, and no-selection empty states appear as in the empty-states wireframe.
- Selecting a session subscribes to it and shows its thread: user messages in a box with the buffer
  font, plain agent messages, dimmer thoughts, one titled line per tool call, and turn errors. The
  borderless editor under the thread sends a prompt, and its button becomes Stop while a turn runs.
- The core reconnects to the daemon until it is up, restores watch and subscriptions after a
  disconnect, and the webview replaces its state from the fresh snapshots without duplicate entries.
- The selection survives closing and reopening the GUI.
- The existing terminal stays reachable through a Terminal row in the sidebar.
- The end-to-end suite covers the agent GUI against the fake server.

The daemon and the wire protocol do not change. When this is done, the check in
`docs/agents/todo.md` passes with Ox.

- `app/src-tauri/src/commands.rs` — `attach_terminal` attaches the terminal in the GUI state file or

- `app/src-tauri/src/gui_state.rs` — `GuiState` and `Selection::Terminal`, keyed by socket path.

- `app/src/App.tsx`, `app/src/components/TerminalPane.tsx` — the terminal view. `TerminalPane` stays
  and becomes one of the views the selection chooses.
- `app/src/ipc/index.ts` — `request()`, `attachTerminal()`, and `terminalInput()` over `invoke`.
- `crates/ur-client/src/client.rs` — `Client::events()` ends when the socket connection ends, which
  is how the Link notices a disconnect. `Client::request()` fails with "the connection to the daemon
  closed" once it has.
- `crates/ur-client/src/protocol.rs` — `Request::Watch`, `Subscribe`, `Prompt`, `Cancel`; the
  events; `SessionSummary` with `title` and `updated_at`; `Entry`. `Subscribe` from the same socket
  connection again replaces the earlier subscription and resends the session snapshot.
- `crates/ur/src/cli/read.rs` and `cli/mod.rs` — daemon clients that install `events()` before

- `Makefile`, `AGENTS.md` — `check-app` runs `pnpm -C app build`. The reducer's unit tests join it.

## Decisions

### The core reconnects and replays the desired set

`Link` holds the socket path, `Desired { watch: bool, subscribed: BTreeSet<SessionId> }`, and the
current `Option<Client>`, each behind a std mutex. `Link::run(app: AppHandle)`, spawned from the
builder's `setup`, loops:

1. Connect with `Client::connect`, retrying every `RETRY_DELAY` (500 ms) until it succeeds.
2. Take `client.events()` before anything else, store the client, and emit `connection`.
3. Replay the desired set: send `watch` when `desired.watch`, then `subscribe` for each session in
   `desired.subscribed`. The daemon answers each with a fresh snapshot, which the webview uses to
   replace its state.
4. Forward events until the receiver ends: `watch_snapshot`, `workspace_added`, `workspace_removed`,
   and `session_changed` under the Tauri event name `watch`; `session_snapshot`, `entry`, and
   `session_removed` under `session`. `terminal_exited` is not forwarded; the terminal attachment
   path already ends its output.
5. Clear the client, emit `connection`, and start over.

Every session's events share the one Tauri event name `session`, and the webview dispatches on the
payload's `session` field. Tauri event names allow only alphanumerics, `-`, `/`, `:`, and `_`, and
session IDs are opaque, so a name that carries the session ID is not safe. This departs from GUI
architecture in `docs/agents/architecture.md`, which is updated.

The `request` command:

- `Watch` sets `desired.watch`, and `Subscribe` adds to `desired.subscribed`. Then, when connected,
  it sends the request; otherwise it answers `Done`, because the replay after the next connect sends
  it. The webview never reads these responses for their snapshots, which arrive as events.
- Every other request is sent when connected and answers the error `not connected to the daemon`
  otherwise. A request interrupted by a disconnect reports the daemon client's error and is not
  resent, as GUI architecture says.

`connection` is a Tauri event and a command with the same payload,
`Connection { connected: bool,
socket: String }`. The command gives the webview the current value
when it starts, since an event emitted before its listener is installed is lost. The `socket` is the
path the no-connection state shows.

The desired set has no terminal attachments or focus yet. Terminals do not survive a daemon restart,
and focus belongs to Attention in the GUI. After a disconnect the whole window shows the
no-connection state, which unmounts the terminal view; when the selection comes back, the terminal
view attaches again through `attach_terminal`, which opens a new terminal when the saved one is
gone.

### The GUI state file holds the terminal and the selection

`GuiState` keeps one `Saved { terminal: Option<TerminalId>, selection: Option<Selection> }` per
socket path. `Selection` becomes `Terminal | Session(String)`, serialized as
`{ "type": "terminal" }` or `{ "type": "session", "session": "..." }`, and exported to TypeScript
with `ts-rs` like the wire protocol types. `Connection` is exported the same way. The app crate is
already in `cargo test --workspace`, so `TS_RS_EXPORT_DIR` from `.cargo/config.toml` applies.

- `attach_terminal(rows, cols, output)` attaches `saved.terminal`, or opens a new terminal, attaches
  it, and saves it. It no longer touches the selection.
- `selection()` returns the saved selection, and `select(selection)` saves it. The webview calls
  `select` whenever the selection changes.

Delete `gui.json`, as `AGENTS.md` says, instead of migrating the old `Selection::Terminal(id)`.

### The sidebar

`Sidebar` renders the watch store: a "Workspaces" header, each workspace with its sessions, and a
"Terminal" row below the workspaces. Workspaces keep the order of the watch snapshot with later
`workspace_added` appended, which is creation order. Sessions within a workspace are ordered by last
activity, newest first; a session without a last activity is treated as newest, because it was
created during this ACP connection and has had no `session_info_update`. Last activity strings are
compared as strings, which works for the RFC 3339 timestamps in one time zone that ACP servers send.
A session shows its session title, or "New session" when it has none.

The Terminal row selects the GUI's one terminal until Workspace terminal controls lists terminals
under their workspaces. It exists so the terminal stays reachable and the end-to-end suite keeps
passing. The selected row, session or Terminal, is highlighted.

Status, unread, attention ordering, and counts belong to Attention in the GUI.

### Stores outside React

`app/src/store/watch.ts` holds
`WatchState { connected: boolean; socket: string; workspaces:
Workspace[]; sessions: SessionSummary[] }`
and `app/src/store/sessions.ts` holds a `Map<string,
ThreadState>`. Each is a small external store:
a current value, a `subscribe(listener)`, and an `apply(event)` that replaces the value with the
result of a pure reducer. Components read them with `useSyncExternalStore`. No store library is
added.

Each store installs its Tauri listener when its module loads, which is before any component renders,
so a listener exists before `App` requests the watch snapshot or a session subscribes.
`connected: false` clears the workspaces and sessions, and the next watch snapshot fills them again.
The session store keeps every session's thread state, so reselecting a session does not refetch.

`useSession(id)` sends `subscribe` the first time a session is used and never unsubscribes: the wire
protocol has no `unsubscribe`, and keeping subscriptions matches the store keeping every thread. The
desired set grows with the sessions viewed in one GUI run, which is a handful.

### The transcript reducer

`app/src/transcript/blocks.ts` defines the display types:

```ts
type Block =
  | { kind: "user"; text: string }
  | { kind: "agent"; text: string }
  | { kind: "thought"; text: string }
  | { kind: "tool_call"; id: string; title: string; toolKind?: ToolKind; status?: ToolCallStatus }
  | { kind: "error"; message: string };
```

`app/src/transcript/reduce.ts` exports
`reduce(state: ThreadState, event: SessionEvent):
ThreadState`, where
`ThreadState { blocks: Block[] }`, and `applyEntry(blocks, entry)`, which it uses for the snapshot
and each later entry:

- `session_snapshot` builds fresh blocks from its transcript, discarding the old state. This is what
  makes replay after a reconnect or a load free of duplicates.
- `entry` appends one entry.
- `session_removed` drops the session from the store.

`applyEntry`:

- A user prompt entry adds a `user` block with the text of its text parts joined by newlines.
- `user_message_chunk`, `agent_message_chunk`, and `agent_thought_chunk` append their text to the
  last block when it is of the same kind, and otherwise start a new block. Only text content is
  read; images are part of Session management and editor. `messageId` is ignored: chunks of one kind
  that follow each other with nothing between them are one message for this item.
- `tool_call` appends a `tool_call` block with its ID, tool call title, tool kind, and tool call
  status.
- `tool_call_update` finds the block with its ID and replaces the title, tool kind, and tool call
  status it carries as non-null. An update for an ID with no block appends a block with what the
  update carries, using the ID as the title when it has none.
- A turn error entry adds an `error` block.
- Every other update (`plan`, `available_commands_update`, `config_option_update`,
  `session_info_update`, `usage_update`, `current_mode_update`, and the rest) is ignored here; later
  items pass through the ones they need.

The reducer is the only webview code that reads `SessionUpdate` shapes. It runs under vitest, which
is added as a dev dependency with `pnpm -C app test` running `vitest run`. `make check-app` runs it
after the build.

### Thread and editor

`Thread` renders the blocks of the selected session: `user` in a bordered box with the buffer font
(Menlo), `agent` as plain text with preserved line breaks, `thought` the same but dimmer,
`tool_call` as one line with its tool call title, and `error` in the error color. It scrolls to the
bottom when blocks are added. Markdown, expansion, and tool call icons belong to Thread rendering.

`Editor` is a borderless textarea with the placeholder "Message agent" and one button. Enter sends,
and Shift+Enter inserts a newline. While the session's status in the watch store is `Working` or
`NeedsPermission`, the button is Stop and sends `cancel`; otherwise it is Send and sends `prompt`
with one text content block, then clears the textarea. A `busy` or `error` response, or a failed
command, shows its message under the textarea until the next send.

### Layout and empty states

`App` reads the connection with the `connection` command and the selection with `selection()` on
mount, then sends `watch`. It renders:

- While not connected: the whole window shows a spinner, "Connecting to <socket>", and "Start the
  daemon with `ur daemon`".
- The sidebar and, to its right: "No workspaces" with `ur workspace add <name> <path>` when there
  are no workspaces and no terminal is selected; "Select a session" when nothing is selected; the
  thread and editor for a selected session; `TerminalPane` for the Terminal row.

A selected session that is no longer in the watch store, because its workspace was removed or the
daemon restarted without it, falls back to no selection. The native window title bar is the title
bar in the wireframe; nothing is drawn for it.

### End-to-end tests against the fake server

The agent GUI's behavior is tested end to end: the daemon, the core, and the webview together,
against the fake server the harness's config file already launches. `openGui()` waits for the
sidebar to render. `Gui.showTerminal()` clicks the Terminal row when no xterm.js element is on the
page, since a reopened GUI restores the Terminal selection, and waits for the terminal to render;
the terminal tests call it. `Gui.lines()` and `Gui.type()` are unchanged: the terminal view is the
only xterm.js on the page.

The daemon restart test needs the session's saved history to outlive the fake server process, which
the daemon restarts with it. `ur-fake-server` takes an optional file argument:
`SavedHistory::file()` reads the saved history from it and writes it back after every change. The
harness's config file passes `history.json` in the test's directory.

The harness gains `TestEnvironment.ur()`, which runs the command line, `newSession()`, which adds
the `home` workspace and creates a session in it, and `stopDaemon()` and `startDaemon()`; and
`Gui.click()`, `texts()`, `waitForText()`, `waitForNone()`, `sendPrompt()`, which types into the
editor and presses Enter, and `request()`, which sends a request through the core's `request`
command.

- `Saved { terminal, selection }` — one socket path's record in the GUI state file.
- `Selection::Terminal`, `Selection::Session(String)` — the selection.
- `selection()`, `select()`, `connection()` — the new core commands.
- `watch`, `session`, `connection` — the Tauri event names.
- `WatchState`, `ThreadState`, `Block` — the webview's store and display types.
- `reduce()`, `applyEntry()` — the transcript reducer's functions.
- `reduceWatch()` — the watch store's reducer.
- `useSession(id)`, `useWatch()`, `useThread(id)` — the hooks over the stores.
- Terminal row — the sidebar row that selects the GUI's terminal.

## Test plan

Unit tests under vitest, table-driven where one behavior covers several inputs:

- `app/src/transcript/reduce.test.ts`:
  - `a_snapshot_replaces_the_thread`: reducing a snapshot over a state that already holds the same
    entries yields the blocks once.
  - `consecutive_chunks_form_one_block`, cases for agent message, thought, and replayed user message
    chunks, and for a kind change starting a new block.
  - `a_user_prompt_joins_its_text_parts`.
  - `tool_call_updates_merge_by_id`, cases for a status change, a title change, a null field left
    unchanged, and an unknown ID appending a block.
  - `a_turn_error_is_an_error_block`.
  - `other_updates_are_ignored`, cases for `session_info_update` and `available_commands_update`.
- `app/src/store/watch.test.ts`:
  - `sessions_order_by_last_activity`: newest first, and a session without one first.
  - `a_removed_workspace_drops_its_sessions`.
  - `a_disconnect_clears_the_watch_state`.

No Rust test changes: the daemon and wire protocol are unchanged, and the core's commands are thin.

End-to-end tests in `app/e2e/session.test.ts`:

- `the empty states follow the workspaces and the selection`: No workspaces, then Select a session
  once a workspace exists.
- `a session created from the CLI answers a prompt sent from the editor`: the user message and the
  fake server's reply render in the thread.
- `Stop cancels a running turn`: Stop during the `tool` script's permission request ends the turn,
  and the button becomes Send.
- `the selected session and its transcript survive closing and reopening the GUI`.
- `the GUI reconnects after a daemon restart without duplicating the thread`: the no-connection
  state shows while the daemon is down; after it restarts, the thread holds one user message and one
  reply, and a new prompt works.

The two terminal tests call `Gui.showTerminal()` and are otherwise unchanged. Run the check in
`docs/agents/todo.md` with Ox by hand: add a workspace and create a session from the CLI, prompt it
and read the reply in the GUI; close and reopen the GUI to see the same session and transcript;
restart the daemon with the GUI open and confirm the thread has no duplicates and a new prompt
works.
